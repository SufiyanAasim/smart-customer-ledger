# v6.0.0 — Shard

**v6.0.0 — Shard is the final and latest release in the planned six-release roadmap.**

## Overview

Shard demonstrates logical sharding: branch data is routed deterministically to one of
several independent MySQL databases via `IShardResolver`, with shard-aware DbContext
creation, a cross-shard reporting service that queries every active shard independently and
handles partial failure explicitly, and full documentation of the rebalancing and
cross-shard-transaction limitations that come with this pattern. As with Replica, this
release is additive and demonstrative — the main application's CRUD workflows continue to
run against the single `customerledger` database from Index onward; Shard adds a
self-contained routing/aggregation layer alongside it rather than migrating the whole
application to a multi-database architecture, which would be a substantially larger and
riskier change than this release's scope justifies.

## Objectives

- Implement `IShardResolver` with deterministic branch-to-shard routing, encapsulated so no
  controller or service computes a modulus or picks a connection string itself.
- Implement shard-aware `ApplicationDbContext` creation for a resolved shard.
- Implement cross-shard report aggregation that reports partial failure explicitly instead
  of silently returning an incomplete result with no indication anything was missed.
- Document data movement/rebalancing, cross-shard transaction limitations, and a shard key
  analysis, honestly describing what plain modulus routing costs.

## Added

- `ShardDescriptor` (Application/DTOs): `ShardId`, `Name`, `ConnectionStringName`, `IsActive`.
- `IShardResolver`/`ShardResolver` (Infrastructure/Sharding): reads the shard registry from
  `ShardSettings:Shards` in configuration, routes via `branchId % activeShardCount` over
  shards ordered by `ShardId` (stable across restarts), throws `BusinessRuleException` if no
  active shards are configured.
- `IShardDbContextFactory`/`ShardDbContextFactory` (Infrastructure/Sharding — not
  Application, since it exposes `ApplicationDbContext` directly, an EF Core concern):
  creates a fresh `ApplicationDbContext` pointed at a resolved shard's connection string.
- `ICrossShardReportingService`/`CrossShardReportingService`: queries
  `vw_BranchRevenueSummary` against every active shard's own connection independently (each
  wrapped in its own try/catch with a 10-second per-shard timeout), aggregates successful
  rows, and reports any failed shard explicitly via `ShardFailure` rather than dropping it
  silently from the total.
- Web UI: Admin → Shard Status lists the registered shards and runs the cross-shard report,
  showing "Complete" vs. "Partial — N shard(s) failed" and which shard(s) failed and why.
- `database/sharding/`: `Shard01Schema.sql`/`Shard02Schema.sql` (which existing schema
  scripts to run against each shard database — schema is identical across shards, only data
  is partitioned), `ShardMetadata.sql` (an illustrative database-table-backed shard
  registry, for a production system that outgrows static configuration — not applied to
  this project's actual schema), `ShardRoutingExamples.sql` (the routing algorithm in raw
  SQL, worked examples), `CrossShardReporting.sql` (the manual two-connection MySQL
  Workbench equivalent of what `CrossShardReportingService` automates).
- `ShardResolverTests` (5 unit tests, no DB dependency): deterministic routing, different
  branches can resolve to different shards, inactive shards excluded, no-active-shards
  throws, `GetAllShards` returns both active and inactive entries.

## Changed

Nothing in existing write-path code. Shard is purely additive, like Replica before it.

## Database Changes

None to the application's own schema/migration. `database/sharding/*.sql` documents how to
stand up additional, independent shard databases using the *existing* schema scripts
unmodified — sharding partitions data across databases, it does not change the schema
within any one of them.

## Security

- Cross-shard visibility (`ShardStatusController`) is Administrator-only — an
  organization-wide capability, consistent with the project's existing "Administrators may
  access multiple branches where explicitly allowed" rule.
- Shard-aware authorization is derived directly from existing branch-level authorization:
  because the routing key is `BranchId`, and `ICurrentUserContext.CanAccessBranch` already
  gates every branch-scoped operation, there is no separate "shard permission" to bypass —
  a user who cannot access a branch cannot access that branch's shard by construction.
- Each shard's connection string is a distinct, independently-configured secret — a
  compromised shard's credentials do not grant access to another shard's database.

## Known Limitations (honestly, not glossed over)

- **Plain modulus routing reshuffles branches when the shard count changes.** Adding or
  removing a shard changes `activeShardCount`, which changes `branchId % activeShardCount`
  for most branches — see `ShardRoutingExamples.sql`'s worked example showing branches 3
  and 4 landing on different shards when going from 2 to 3 shards. A production system
  would use consistent hashing or the explicit `BranchShardAssignments` table sketched in
  `ShardMetadata.sql` to avoid this.
- **No distributed transactions across shards.** A normal EF Core / MySQL transaction is
  scoped to one connection, hence one shard. This project keeps all of one branch's
  financial data on a single shard specifically so that Balance-release transactional
  guarantees (row locking, atomicity) continue to hold — a workflow that needed to update
  two branches' data atomically, if those branches lived on different shards, would need a
  saga/compensating-action pattern this project does not implement.
- **Rebalancing (moving one branch to a different shard) is a manual, documented procedure,
  not an automated one**: export the branch's rows (Snapshot release's export tooling),
  import them into the target shard, update the shard registry/assignment, and only then
  cut over routing — see the Rebalancing section below.
- **The main application's CRUD workflows are not actually sharded** — Customers,
  Invoices, Payments, etc. still all live in the one `customerledger` database used since
  Index. Shard's routing/aggregation layer is demonstrated in isolation (Admin → Shard
  Status) rather than retrofitted through every existing controller, which would be a much
  larger, riskier change than this release's scope justifies for a course project.
- Only one report (`vw_BranchRevenueSummary`) is wired through
  `ICrossShardReportingService` — the same scope-limiting choice made for
  `IReplicaAwareReportingService` in v5.0.0.

## Rebalancing Procedure (documented, not automated)

1. **Export** the branch's data using Snapshot's export tooling (`ExportService`) or a
   direct `mysqldump --where="BranchId=<id>"`-style extraction per table.
2. **Import** that data into the target shard database (already running the same schema —
   see `Shard01Schema.sql`/`Shard02Schema.sql`).
3. **Verify counts and balances** match between source and destination before cutting over
   — compare `SELECT COUNT(*)` and `SUM(TotalAmount)` per table on both sides.
4. **Freeze routing temporarily**: during the cutover window, reject writes for the branch
   being moved (a maintenance-mode flag, not implemented in this release) so no write lands
   on the old shard after the copy is taken.
5. **Update the shard registry** (`ShardSettings:Shards` in configuration, or the
   `BranchShardAssignments` table if a production system uses that instead) so
   `IShardResolver` now routes the branch to its new shard.
6. **Remove the old shard's copy** of that branch's data only after confirming the new
   shard is serving correctly.
7. **Rollback procedure**: if step 5's cutover reveals a problem, revert the registry change
   (routing immediately goes back to the old shard, whose data was never deleted until
   step 6) — this is why step 6 is deliberately last and separate from step 5.
