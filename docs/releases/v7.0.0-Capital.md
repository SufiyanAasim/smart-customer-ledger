# v7.0.0 — Capital

**This release was not part of the original six-release roadmap** (Index → Balance →
Snapshot → Chronicle → Replica → Shard, with Shard marked as the final planned release). It
was requested separately, mid-project, as an explicit addition: incorporate a real AI/ML or
data-mining concept, alongside analytics, somewhere in the system. This document exists so
that addition is tracked with the same honesty discipline as every other release —
including what was actually verified versus what could not be, in this environment.

## Overview

Capital adds two real, working analytics techniques on top of the existing transactional
data, both dependency-free (no ML framework, no external service call):

1. **Customer payment-risk scoring** — a logistic regression classifier, implemented from
   scratch (feature normalization, sigmoid, batch gradient descent), trained fresh on each
   request against the current branch's (or, for an Administrator, the organization's)
   customer data.
2. **RFM (Recency/Frequency/Monetary) customer segmentation** — a standard, widely-taught
   data-mining technique that buckets customers into named segments (Champions, At Risk,
   Lost, etc.) by quartile-scoring their recent activity, purchase frequency, and spend.

Both are demonstrated behind a single Admin/Branch-Manager-only **Analytics** screen.

## Objectives

- Implement a genuine, from-scratch machine learning algorithm (not a rule engine dressed
  up as ML) — weights are *learned* from data via gradient descent, not hand-tuned.
- Implement a genuine data-mining/segmentation technique with a defensible, standard
  methodology (RFM), not an ad hoc scoring formula.
- Keep both dependency-free, given this environment's constraints (no verified network
  access to restore a multi-hundred-megabyte ML framework, no live MySQL to source a large
  real training set).
- Be explicit about every simplification made versus a production system, rather than
  presenting a course demonstration as a finished credit-risk product.

## Added

- `LogisticRegressionModel` (Application/Services): z-score feature normalization, sigmoid
  activation, batch gradient descent over binary cross-entropy loss. Fully unit tested,
  including a linearly-separable synthetic dataset the model must learn to classify
  correctly, and a multi-feature dataset checked for monotonic risk ordering.
- `CustomerRiskFeatures`/`CustomerRiskScore` DTOs and `ICustomerRiskScoringService`/
  `CustomerRiskScoringService`: extracts five features per customer (credit utilization,
  unpaid-invoice ratio, average invoice amount, total outstanding, customer age in days),
  trains against a heuristic label (currently has an Overdue installment or a Reversed
  payment), and scores every active customer in scope.
- `RfmSegmenter` (Application/Services, pure/static): quartile-based Recency/Frequency/
  Monetary scoring and rule-based segment naming. Fully unit tested, including a
  synthetic dataset with a clear "Champion" and a clear "Lost" customer.
- `CustomerRfmInput`/`CustomerRfmSegment` DTOs and `ICustomerSegmentationService`/
  `CustomerSegmentationService`: computes Recency (days since last completed payment, or
  since registration if none), Frequency (invoice count), and Monetary (total completed
  payments) per customer.
- Web UI: `/Analytics` (Administrator/Branch Manager) shows the risk-score table (with the
  raw feature values alongside each score) and the RFM segment breakdown with counts per
  segment.
- `database/analytics/CreateAnalyticsViews.sql`: `vw_CustomerRiskFeatures`, an additional
  (non-required) view exposing the same five raw features the C# service computes, plus the
  heuristic label's derivation, directly queryable in MySQL Workbench.
- 7 new unit tests (`LogisticRegressionModelTests`, `RfmSegmenterTests`) — all pass with
  zero external dependency.

## Security

- The Analytics screen is Administrator/Branch-Manager only (`[Authorize(Roles = ...)]`) —
  cashier/staff cannot see risk scores or segments.
- Branch isolation is preserved: both services scope to the current user's branch unless
  they are an Administrator, exactly like every other reporting service in this project.
- No customer data leaves the process — training and inference both happen in-memory,
  in-request; nothing is sent to an external ML API.

## Known Limitations (stated plainly, not glossed over)

- **The training label is a same-day heuristic, not a real historical outcome.** "High
  risk" is defined as *currently* having an overdue installment or a reversed payment —
  this project has no labeled history of "did this customer eventually default" to train
  against, because it doesn't track long-run customer outcomes as a distinct dataset. A
  production credit-risk model would need that real historical label, ideally collected
  over months/years, not synthesized from the current state of the same database it reads
  features from.
- **The model retrains from scratch on every request rather than being persisted.** At this
  project's data scale (tens to low thousands of customers per branch) this is fast enough
  to not matter, but it means predictions can shift slightly between two closely-timed
  requests if data changed in between — there is no versioned, frozen model artifact.
- **No train/test split** — the model is trained and scored on the same customer set
  (transductive, not a held-out evaluation). This is appropriate for an operational
  "who looks risky right now" screen, but it is not a rigorous accuracy evaluation, and no
  accuracy/precision/recall metric is reported anywhere in this release.
- **RFM's quartile thresholds are recomputed per request from whichever customer set is in
  scope** — a branch with only 3 customers produces coarse, less meaningful quartiles than
  one with 300. The technique is standard; the sample size caveat applies to any RFM
  implementation, not just this one.
- **No feature beyond the five listed is considered** — no seasonality, no branch-level
  comparison baseline, no macroeconomic signal. This is intentionally a small, explainable
  feature set suited to a course-level demonstration.
- This release exists outside the base project specification's six-release roadmap — grade
  it as a bonus/extension, not as satisfying any of the six releases' core requirements.
