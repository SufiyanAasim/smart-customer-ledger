# v2.0.0 — Balance

## Overview

Balance completes the financial core that Index left as a foundation: every money-moving
operation — activating an invoice, posting a payment, reversing a payment, paying an
installment, reconciling drift — now runs inside a real database transaction, keeps the
invoice and the customer's account balance in lock-step, and is protected against
concurrent overpayment by an explicit row lock. Nothing here changes the schema Index
shipped; it activates the arithmetic and safeguards that schema was built to support.

## Objectives

- Keep `Invoice.PaidAmount/OutstandingAmount/PaymentStatus` and
  `CustomerAccount.TotalBilled/TotalPaid/CurrentBalance` synchronized on every financial
  event, inside one transaction per event.
- Make optimistic concurrency (`ConcurrencyVersion`) actually detect conflicts, by
  incrementing it on every mutation.
- Implement payment reversal without ever deleting the original payment row.
- Implement installment payment processing that reuses the payment-posting code path
  rather than duplicating its arithmetic.
- Implement account reconciliation that recalculates from source rows and reports/corrects
  drift.
- Demonstrate all four ACID properties with runnable SQL and an automated concurrency test.

## Added

- `InvoiceService.ActivateAsync`/`CancelAsync` now sync `CustomerAccount.TotalBilled` and
  `CurrentBalance` inside a transaction (TotalBilled is recognized at Activate — the moment
  an invoice becomes real debt — not at Draft creation).
- `PaymentService.RecordPaymentAsync` locks the invoice row with
  `SELECT ... FOR UPDATE`, then updates the invoice and the customer account together.
- `PaymentService.ReverseAsync`: validates the payment is Completed and not already
  reversed, requires a reason, creates a linked reversal row, and resyncs invoice/account
  totals — all under the same row lock discipline.
- `IInstallmentScheduleService.PayInstallmentAsync`: applies a payment to one schedule row
  by delegating the actual money movement to `PaymentService.RecordPaymentAsync`, then marks
  the row (and, once every row is settled, the parent plan) accordingly.
- `OverdueInstallmentBackgroundService`: an hourly `BackgroundService` that flips Pending
  rows whose due date has passed to Overdue — the "explicit scheduled mechanism" the project
  spec requires, since no trigger fires from the mere passage of time.
- `IReconciliationService`: recalculates a customer account's totals purely from active
  invoices and completed non-reversed payments, corrects any drift, and writes an
  `AuditLogs` entry recording the before/after values.
- Web UI: payment reversal form (Admin/Branch Manager only) on the payment details page,
  a "Pay" action per pending installment schedule row, and an Admin → Reconciliation screen
  that runs and reports on an entire branch.
- SQL: `database/transactions/InvoiceTransaction.sql`, `PaymentTransaction.sql`,
  `PaymentRollbackDemo.sql`, `PaymentReversal.sql`, `Reconciliation.sql`, and
  `ACID-Demonstrations.sql` — a guided tour of Atomicity/Consistency/Isolation/Durability
  with concrete statements to run.

## Changed

- `InvoiceService.ActivateAsync` and `CancelAsync` are now transactional and mutate
  `CustomerAccount` — previously (Index) they only touched the invoice.
- Every service method that mutates `Invoice` or `CustomerAccount` now increments
  `ConcurrencyVersion` explicitly. Without this, EF Core's optimistic-concurrency check
  would compare a column that never changes and could never detect a conflict — this was a
  latent gap in Index, closed here.

## Database Changes

None — no new tables, columns, or migrations. Balance is a business-logic and SQL-script
release built entirely on the Index schema.

## Security

- Payment reversal is restricted to Administrator/Branch Manager roles
  (`[Authorize(Roles = ...)]` on `PaymentsController.Reverse`).
- Every new transactional method re-checks `ICurrentUserContext.CanAccessBranch` before
  mutating data — branch isolation from Index is preserved, not bypassed by the new
  workflows.
- No new SQL surface area introduces string concatenation — `FromSqlInterpolated` is used
  for the two raw `FOR UPDATE` queries, which parameterizes the interpolated value
  automatically (it is not string-concatenated SQL).

## Known Limitations

- Reconciliation is on-demand (Admin-triggered), not scheduled — an automatic nightly sweep
  is a reasonable Snapshot/Replica-era addition, not implemented here.
- `PayInstallmentAsync` applies one payment to exactly one schedule row; splitting a single
  payment across multiple overdue installments in one submission is not implemented.
- No customer-facing "pay online" flow — payments and installment payments are recorded by
  staff, matching the in-person retail workflow this project models.
