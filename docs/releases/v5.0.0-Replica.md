# v5.0.0 — Replica

## Overview

Replica demonstrates read/write separation: a dedicated read connection for non-critical
reporting, a health check that decides per-call whether the replica is usable, and
transparent (logged, never silent) fallback to the primary connection when it isn't. Given
this environment cannot guarantee a second MySQL server is available to configure as a true
replication target, this release ships in **simulated mode** by default — clearly labeled as
such throughout the code and documentation, per this project's standing "do not claim a
capability that doesn't exist" discipline — while also fully documenting the native MySQL
replication configuration for a real multi-server deployment.

## Objectives

- Add a primary (write) and a read-only (replica) database connection, each connection-pooled.
- Route all writes through the existing services (unchanged — they use `ApplicationDbContext`).
- Add a health check that determines, on every call, whether the replica is reachable.
- Add at least one reporting query that prefers the replica and falls back to the primary,
  with the fallback logged and surfaced in the UI.
- Document both a real native-replication setup and this release's simulated default,
  without conflating the two.

## Added

- `ReplicaDbContext`: shares `ApplicationDbContext`'s exact EF Core model (same entities,
  same `OnModelCreating`) but is registered separately in DI with its own connection
  string, `ConnectionStrings:ReplicaConnection` — the standard EF Core pattern for two
  contexts, one model. Falls back to `DefaultConnection` if `ReplicaConnection` is unset.
- Both `ApplicationDbContext` and `ReplicaDbContext` are registered via `AddDbContextPool`
  (not `AddDbContext`) for real connection pooling, not just a documented intention.
- `IReplicaHealthService`/`ReplicaHealthService`: calls `Database.CanConnectAsync()` against
  the replica connection with a 3-second timeout on every invocation — health is never
  assumed or cached across requests.
- `IReplicaAwareReportingService`/`ReplicaAwareReportingService`: reads
  `vw_BranchRevenueSummary` via `MySqlConnector` against whichever connection string the
  health check currently selects, branch-scoped for non-administrators, and returns a
  `ReplicaAwareResult<T>` wrapper so callers (and the UI) can see which connection actually
  served the data.
- Web UI: Admin → Replica Status shows the current health state and which connection served
  the branch revenue report.
- `database/replication/`: `PrimarySetup.sql` and `ReplicaSetup.sql` (real native MySQL
  replication configuration — `server-id`, binary logging, `CHANGE REPLICATION SOURCE TO`,
  GTID auto-positioning), `SimulatedReplicaSync.sql` (this release's actual default —
  periodic `mysqldump | mysql` batch resync, explicitly labeled as *not* continuous
  replication), and `VerifyReplication.sql` (verification for both modes).

## Changed

Nothing in existing write-path code — every service that mutates data still uses
`ApplicationDbContext` exactly as before. Replica is purely additive.

## Database Changes

None — `ReplicaDbContext` shares `ApplicationDbContext`'s model exactly (confirmed via the
same empty-migration-diff technique used in every prior release, run explicitly against
`--context ApplicationDbContext` since two DbContext types now exist in the project).

## Security

- The replica connection is used for reads only — no service ever calls `SaveChanges` on
  `ReplicaDbContext`; there is no application code path that could accidentally write
  through it.
- Branch isolation is preserved: `ReplicaAwareReportingService` still scopes the report to
  the current user's branch unless they are an Administrator.
- Health-check failures are logged (`ILogger`), not swallowed silently, so an operator can
  see when and how often fallback is happening.

## Known Limitations

- **Simulated mode is the shipped default** — it demonstrates the read/write separation
  *pattern* (health check, fallback, routing), not real sub-second replication lag or
  automatic failover. Do not present it as production-grade high availability.
- Only one reporting query (`vw_BranchRevenueSummary`) is wired through
  `IReplicaAwareReportingService` in this release — extending the pattern to the other five
  views is straightforward but not done here, to keep this release's scope reviewable.
- No automatic promotion of a replica to primary on failure — that is out of scope for a
  read-replica pattern and belongs to a full HA/failover design, which this project does
  not attempt.
- Critical read-after-write operations (e.g. immediately re-displaying an invoice right
  after creating it) intentionally continue to read from the primary via the existing
  services — only clearly "non-critical reporting" reads were moved to the
  replica-aware path, per the project specification's own read/write rules.
